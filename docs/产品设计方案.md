# 本地模型中心设计方案

## 1. 目标

做一个运行在本机的轻量模型管理器，解决以下问题：

- 从 Hugging Face、ModelScope、Ollama 等来源搜索和安装常用模型。
- 大文件支持断点续传、并发下载、代理、失败自动重试和完整性校验。
- 自动识别模型类型、量化格式、硬件要求、许可证和可用运行时。
- 本地统一管理模型位置，避免 ComfyUI、MLX、Ollama 各存一份。
- 下载完成后能直接启动或调用模型，而不是“文件下载完但不能用”。
- 保留任务日志、错误原因和恢复入口，后续换机器也能复用。

目标平台是 Windows、Linux 和 macOS，三者使用同一份 Go 后端、同一份 SQLite 数据格式和同一套 Web 界面。Apple Silicon/MLX、NVIDIA/CUDA 和 CPU 是第一版重点识别的三类能力；AMD/Intel GPU 作为可插拔能力逐步补充。模型推荐面向所有支持的机器，不绑定当前这台 M4 Max。

## 1.1 跨平台原则

- 后端只依赖 Go 标准库和纯 Go SQLite，不要求用户安装 Python、Node.js、Docker 或 aria2。
- 前端构建产物用 `go:embed` 嵌入 Go 二进制，发布为 Windows、Linux、macOS 各自的单文件程序。
- 文件路径、代理、进程启动、系统自启动和硬件探测全部通过 OS Adapter 隔离。
- 外部运行时可以被检测和调用，但不是 ModelDock 自身的启动前置条件。
- 模型文件和数据库路径都使用用户选择的目录，不把路径写死在项目目录或用户家目录。

| 平台 | 发布形式 | 重点能力 |
|---|---|---|
| macOS arm64/amd64 | 单文件二进制，可选 DMG/LaunchAgent | Apple Silicon、统一内存、Metal、MLX |
| Windows amd64/arm64 | `.exe`，可选 MSI | NVIDIA CUDA、DirectML、CPU、独立显卡显存 |
| Linux amd64/arm64 | 单文件二进制，可选 deb/AppImage | NVIDIA CUDA、AMD ROCm、CPU、服务器/NAS |

## 2. 产品形态

### 2.0 内容创作工作台

ModelDock 将内容创作拆成两个独立工作台，共用模型索引、运行时、素材目录、任务队列和导出能力。

#### 短视频工作台

面向单条视频的快速生产，流程为“创作输入 -> 主题拆解 -> 分镜草稿 -> 图片/视频/配音/音效素材 -> 字幕与时间线 -> 导出”。用户可以选择竖屏 9:16、横屏 16:9 或方形 1:1，设置时长、视觉风格、配音和字幕。每个镜头可以独立重新生成，不影响其他镜头。

#### 短剧工作台

面向多集连续剧情，流程为“项目概览 -> 剧本拆解 -> 角色卡 -> 场景卡 -> 分集 -> 分镜 -> 镜头素材 -> 配音字幕 -> 成片”。角色卡保存外观、服装、年龄和参考图，场景卡保存地点、时间、光线和构图；连续性检查用于发现角色、服装、场景和剧情关系在不同镜头间的变化。

两类工作台都通过现有模型交互和运行时适配器执行任务。短视频优先快速出片，短剧优先保留项目结构和跨镜头一致性；生成失败、运行时中断和导出任务都进入统一任务中心。

工作台不得把模型名称写死。每个工作台维护模型角色配置：脚本/分镜模型、图片参考模型、视频生成模型、配音/音频模型。候选项来自本地已纳入管理且可用的模型，依据任务能力给出默认推荐，用户可以手动切换；没有匹配模型时显示配置入口和原因。短视频的“生成视频素材”提交统一异步 Job，复用模型交互的阶段、轮询、结果预览和错误处理。

采用“桌面窗口 + 浏览器服务 + CLI”三种入口，共用同一个 Go 核心：

- **桌面模式**：启动程序直接打开原生窗口，不要求用户手动打开浏览器。
- **服务模式**：只启动本地 HTTP 服务，适合 NAS、Linux 服务器、远程管理和无图形界面环境。
- **CLI 模式**：适合脚本、自动化和故障排查，例如 `modelhub install ...`、`modelhub status`。
- SQLite 保存模型元数据、下载任务、运行配置和日志索引，不保存模型权重。
- 桌面程序、服务程序和 CLI 共用同一个 Go 核心、数据库格式和配置目录。

### 2.1 桌面技术选择

优先采用 **Wails + Vue3**：

- Go 直接作为应用后端，Vue/Vite/Ant Design Vue 作为界面。
- 前端构建产物嵌入 Go 应用，启动后通过系统 WebView 显示原生窗口。
- macOS 使用系统 WebKit，Windows 使用 WebView2，Linux 使用 WebKitGTK。
- 不需要随程序捆绑完整 Chromium，安装包和内存占用通常明显小于 Electron。
- Go 方法可以直接暴露给前端，适合下载进度、硬件信息和运行实例控制。

Electron 仍可作为备选，但它会带一套 Chromium 和 Node.js 运行环境，安装包更大、常驻内存更高；本项目没有复杂浏览器兼容需求，不把 Electron 作为默认方案。

### 2.2 双模式启动命令

```bash
modelhub                 # 桌面模式，打开原生窗口
modelhub serve           # 服务模式，只启动 HTTP API
modelhub serve --lan     # 明确要求后才允许局域网访问
modelhub --browser       # 启动服务并用默认浏览器打开页面
modelhub status          # CLI 模式
```

桌面模式内部仍可以启动本地 HTTP/API，但只监听 `127.0.0.1`；窗口关闭时可选择退出服务或继续放到系统托盘。服务模式不依赖 Wails，保证 Linux NAS 和无桌面环境也能运行。

### 2.3 跨平台桌面依赖边界

“单个 Go 二进制”指不需要用户安装 Python、Node.js、aria2 或独立前端服务；桌面 WebView 属于操作系统能力：

- macOS：使用系统 WebKit，通常无需额外安装。
- Windows：优先使用系统 WebView2；首次运行检测缺失并给出安装提示。
- Linux：需要系统 WebKitGTK/GTK 运行库，因此提供 `server` 浏览器模式和 AppImage/发行版依赖说明作为兜底。

这样既有类似 Electron 的独立窗口体验，也不会为了桌面窗口强迫 NAS 或服务器安装图形环境。

## 3. 总体架构

```text
Web UI / CLI
     |
Go API Server
     |
+----+----------------+------------------+
| Catalog             | Task Manager     |
| 模型索引/兼容性      | 队列/重试/日志     |
+---------------------+------------------+
| Source Adapters      | Runtime Adapters |
| HF / ModelScope /    | MLX / Ollama /   |
| Ollama / Local       | llama.cpp /      |
|                     | ComfyUI          |
+---------------------+------------------+
| Storage Manager      | Process Manager  |
| 去重/校验/链接/回收   | 启停/健康检查      |
+---------------------+------------------+
| SQLite + manifest    | 本地模型目录       |
```

### 3.1 后端技术

- Go 1.24+。
- SQLite 使用 `modernc.org/sqlite`，保持单二进制、无需 CGO；数据库迁移由应用自身管理。
- HTTP API 使用标准库或轻量路由，不引入重型框架。
- 前端使用 Vue 3、Vite、TypeScript、Ant Design Vue，构建后用 `go:embed` 嵌入二进制。
- 进程、文件、网络操作全部由后端统一记录，避免前端直接拼接 shell 命令。
- 使用 `//go:build` 为 Windows、Linux、macOS 提供少量平台实现，核心业务代码不分叉。

### 3.2 下载引擎

下载引擎第一版直接用 Go 实现，避免“用户还要另外安装 aria2、Python 或 Node.js”：

1. 使用 Go `net/http` 和 HTTP Range 实现分片、并发和断点续传。
2. 每个文件拆成可恢复的分片，分片状态写入任务目录；完成后原子合并并校验。
3. 支持 HTTP/HTTPS 代理、SOCKS5、`NO_PROXY`、每源代理和全局代理。
4. 支持超时、限速、连接池、指数退避、失败分类和 stalled 检测。
5. Hugging Face 的 Xet/CDN 下载失败时，自动切换普通 `resolve`/LFS 地址或 ModelScope 镜像；不能无限重试同一条失败链路。
6. 可选检测到系统已有 aria2 时使用它，但不能把 aria2 作为必需依赖，也不能把任务状态交给外部进程。
7. 每个文件下载完成后先校验，再将任务标记为完成；模型整体还要通过 manifest 检查。

当前 MiniMax 模型遇到的“进程存在但没有进度”也要被识别：连续一段时间字节数不增长时，任务进入 `stalled`，记录代理、URL、错误和最后吞吐，而不是显示为正常下载。

## 3.3 硬件能力识别与模型推荐

程序启动时生成一份 `HostCapability`，不只显示 CPU 名称，而是转换成可用于推荐的能力标签。推荐系统由三层组成：

1. **硬件探测**：识别当前机器真实拥有的 CPU、内存、GPU、显存和指令/加速后端。
2. **模型需求**：从模型 manifest、配置文件和验证数据中提取最低内存、推荐显存、量化格式、运行时和任务类型。
3. **匹配评分**：计算可运行性、性能预期、内存余量、安装复杂度和验证可信度，输出推荐等级和解释。

### 3.3.1 统一硬件描述

```json
{
  "os": "windows",
  "arch": "amd64",
  "cpu": {"vendor": "intel", "model": "Core i7", "threads": 20},
  "memoryGB": 32,
  "gpus": [{
    "vendor": "nvidia",
    "model": "RTX 4070",
    "vramGB": 12,
    "backend": ["cuda", "directml"],
    "driver": "verified"
  }],
  "capabilities": ["cuda", "avx2"],
  "runtimes": [{"name": "comfyui", "version": "verified"}]
}
```

不同平台的字段统一成同一个结构：

- CPU：厂商、型号、核心/线程、架构、AVX/NEON 等能力。
- 系统内存：总量、可用量、可分配给模型的安全上限。
- GPU：厂商、型号、显存、后端、驱动版本和运行时状态。
- Apple Silicon：芯片型号、统一内存、Metal/MLX 能力。
- 运行时：Ollama、CUDA、ROCm、DirectML、MLX、ComfyUI 等是否已安装和验证。
- 存储：可用容量、读写速度（可选测试）、模型目录位置。

### 3.3.2 模型需求描述

每个模型版本不只记录下载地址，还要记录兼容性信息：

```yaml
model: qwen3-32b
variant: q4_k_m
task: [chat, code]
format: gguf
sizeGB: 19.2
requirements:
  minimumMemoryGB: 24
  recommendedMemoryGB: 32
  recommendedVRAMGB: 12
  backends: [cuda, metal, cpu]
  runtimes: [llama.cpp, ollama]
  contextMemoryGB: 4
validation:
  status: verified
  platforms: [darwin-arm64, linux-amd64, windows-amd64]
```

模型的不同量化版本要作为不同候选项展示，例如 `FP16`、`8bit`、`Q8`、`Q5`、`Q4`，而不是只显示一个模型名称。

### 3.3.3 推荐评分

推荐引擎输出四种结果：

- **推荐**：满足运行时和硬件要求，并有足够余量。
- **可以运行**：能够运行，但速度、上下文长度或显存余量有限。
- **不建议**：理论上可能运行，但容易交换内存、OOM 或速度过慢。
- **不可用**：缺少硬件后端、运行时、指令集或必要组件。

建议评分维度：

```text
总分 = 硬件匹配 35%
     + 内存/显存余量 25%
     + 运行时兼容 20%
     + 已验证可信度 10%
     + 预计性能 10%
```

硬规则优先于分数：如果模型需要 CUDA 而机器没有 CUDA/兼容后端，即使其他分数很高，也不能显示为“推荐”。

推荐结果必须给出理由，而不是只给一个颜色：

```text
推荐：Qwen3-14B Q4_K_M
原因：你的 RTX 4060 8 GB 显存可运行，系统内存 32 GB 足够，llama.cpp 已验证。
替代：Qwen3-32B Q4_K_M 可以加载到系统内存，但预计速度较低，不建议日常使用。
不推荐：Qwen3-32B FP16，需要约 70 GB 显存/内存。
```

### 3.3.4 不同机器的推荐策略

```json
{
  "os": "darwin",
  "arch": "arm64",
  "cpu": "Apple M4 Max",
  "memoryGB": 128,
  "gpu": [{"vendor": "apple", "backend": "metal", "memoryGB": 128}],
  "capabilities": ["mlx", "metal", "unified-memory"]
}
```

识别策略：

- macOS：通过系统 API/`sysctl` 识别 Apple Silicon、统一内存和 Metal 可用性。
- Windows：识别 CPU、物理内存、NVIDIA/AMD/Intel GPU、显存和 CUDA/DirectML 可用性。
- Linux：读取 `/proc`、PCI 信息和可用运行时探测 CUDA/ROCm/Metal 替代能力。
- 探测失败时降级为 CPU，不阻止程序启动；每项能力显示“已验证、已发现、未验证”状态。

推荐引擎根据模型 manifest 和 HostCapability 计算结果：

- Apple Silicon + 统一内存：优先推荐 MLX/MLX-VLM，按统一内存估算可运行尺寸。
- NVIDIA 独立显卡：优先推荐 CUDA、GGUF、Transformers、ComfyUI CUDA 工作流，并按显存过滤。
- AMD GPU：优先推荐 ROCm 可用的运行时；不满足版本要求时提示 DirectML/CPU 备选。
- Intel GPU：优先推荐已声明支持 DirectML/oneAPI 的模型和运行时。
- 无可用 GPU：推荐 GGUF/CPU 量化模型，显示预计速度和内存风险。

典型机器的推荐方向：

| 机器配置 | 优先推荐 | 谨慎推荐 |
|---|---|---|
| Apple Silicon 16-32 GB | MLX 4bit 小模型、GGUF Metal | 30B 以上、视频模型 |
| Apple Silicon 64-128 GB | MLX 4bit/8bit、MLX-VLM、图片模型 | 超大视频模型、未验证量化 |
| NVIDIA 8 GB 显存 | 7B-14B 量化、SDXL、轻量 ComfyUI | 30B、FP16 图片/视频模型 |
| NVIDIA 12-24 GB 显存 | 14B-32B 量化、FLUX/视频模型 | 大尺寸高分辨率批量任务 |
| NVIDIA 48 GB 以上 | 大型量化、FP16、视频工作流 | 只受磁盘和速度限制 |
| 普通 CPU + 16 GB 内存 | 1B-7B GGUF Q4/Q5 | 图像、视频和大上下文模型 |
| Linux/NAS 无 GPU | CPU 量化、Embedding、ASR 小模型 | CUDA/MLX/ROCm 专用模型 |

推荐不能只看模型参数量，还要考虑任务类型：文生图关注显存/统一内存和分辨率，文生视频关注显存、显存带宽和磁盘空间，语音模型关注 CPU 指令集和实时系数，长上下文对话关注 KV Cache 内存。

模型页面必须解释推荐原因，例如“你的 M4 Max 128 GB 统一内存，推荐 MLX 4bit；该模型原生 CUDA 版本不可直接用于 MLX”。

### 3.3.5 推荐数据的可信度

推荐数据分为三类：

- **官方声明**：来自模型卡或运行时文档。
- **社区估算**：根据参数量、量化和上下文计算，标记为估算。
- **本机验证**：实际加载、生成、测速和峰值内存记录。

用户可以选择“保守模式”或“激进模式”：

- 保守模式：预留更多内存，只推荐有验证记录的组合。
- 激进模式：允许接近硬件上限的模型，并明确提示 OOM/交换风险。

本机验证结果只影响当前设备的推荐置信度，不覆盖模型的通用兼容性。

## 4. 模型来源与发现

### 4.1 来源适配器

| 来源 | 第一版能力 | 备注 |
|---|---|---|
| Hugging Face | 搜索、仓库文件清单、revision、下载 | 支持 HF Hub API 和代理；优先处理 safetensors、GGUF、MLX |
| ModelScope | 搜索、仓库文件清单、下载 | 作为 Hugging Face 不稳定时的镜像/替代来源 |
| Ollama Library | 搜索、安装、运行 | 通过 Ollama CLI/API 管理，不复制其 blob |
| 本地目录 | 扫描、识别、导入 | 支持已有 ComfyUI、MLX、Ollama、llama.cpp 目录 |
| 自定义 URL | 下载、校验、登记 | 允许用户提供带认证或签名的直链 |

### 4.2 常用模型目录

内置一个可更新的轻量 `catalog.yaml`，只放推荐信息，不存权重：

- 对话：Qwen、Llama、Mistral、DeepSeek 等。
- Apple Silicon/MLX：mlx-community、MLX-VLM、MLX-Audio 类模型。
- 图片：Stable Diffusion、FLUX、MiniMax H3 Image 等。
- 视频：Wan、LTX、MiniMax H3 Video 等。
- 语音：Whisper、CosyVoice、Qwen-Audio 等。
- ComfyUI：checkpoint、VAE、LoRA、ControlNet、文本编码器。

目录项必须显示：来源、模型大小、量化格式、许可证、推荐内存、支持的运行时、是否需要额外组件、最近验证时间。推荐项和社区搜索结果分开，避免把未经验证的模型展示成“可直接运行”。

## 5. 本地存储设计

首次启动只提供一个默认目录，用户可以在设置中随时增加、切换和迁移模型存储根目录。默认目录按平台推导，不写死某个用户名：

- macOS/Linux：`~/ModelDock`
- Windows：`%USERPROFILE%\\ModelDock`

任意模型根目录都使用以下结构，下面用 `$MODEL_ROOT` 表示用户当前选择的目录：

```text
${MODEL_ROOT}/
├── objects/                 # 按 sha256 存储的文件对象
├── manifests/               # 模型清单和来源快照
├── installs/                # 面向用户的模型目录/软链接
├── runtimes/                # 运行时配置，不放大型运行时缓存
├── logs/                    # 下载和运行日志
└── modelhub.db              # SQLite 数据库
```

运行时不放在模型目录中。模型目录只保存模型权重和来源清单；应用自己的运行时目录按操作系统用户数据目录保存：

```text
macOS:   ~/Library/Application Support/ModelDock/runtimes/
Windows: %LOCALAPPDATA%\\ModelDock\\runtimes\\
Linux:   ~/.local/share/ModelDock/runtimes/
```

运行时目录由 ModelDock 按 `运行时名称 + 平台 + 架构 + 版本` 管理，包含启动器、依赖环境和锁文件。首次使用某个模型时，应用检查运行时是否已准备；缺失时显示组件大小、许可证和安装进度，完成后再执行任务。运行时下载和模型下载是两个独立任务，不能把 Python 虚拟环境、shell 脚本或平台二进制写入模型目录。

迁移到新机器时只需要重新扫描或导入模型根目录，ModelDock 根据本机系统和硬件重新准备兼容运行时。旧版本遗留在模型目录中的 `generate-image.sh`、`generate-video.sh` 仅作为兼容入口，发现后可以迁移到应用运行时目录；新安装不再依赖这些文件存在。

数据库和模型文件默认放在同一个根目录，也可以单独指定数据库位置。存储根目录记录为逻辑 ID，不把绝对路径写进模型 manifest；换盘或换机器后可以重新绑定目录。

存储管理必须支持：

- 增加多个存储根目录，并设置默认下载目录。
- 显示每个目录的总空间、可用空间、模型数量和当前任务。
- 将模型从 A 迁移到 B，迁移完成并校验后才更新数据库。
- 暂停任务后切换存储目录，已下载分片可以继续复用。
- 启动时扫描外置硬盘、NAS 挂载目录和已有 ComfyUI/MLX 目录。
- 存储目录不可用时只标记为 `offline`，不删除数据库记录。
- Windows 不依赖 Unix 软链接；优先使用硬链接，无法使用时使用复制或 junction，并明确显示占用空间。
- 跨磁盘硬链接不可用时使用对象复制，避免用户以为模型已去重。

模型不直接复制到多个应用目录。通过对象存储 + 硬链接/软链接提供给：

- MLX 项目；
- ComfyUI models 目录；
- llama.cpp/GGUF；
- 自定义脚本；
- Ollama 外部模型目录（不能安全链接时明确提示会产生一份副本）。

每个模型保存一个 manifest：

```json
{
  "id": "nativ-community/MiniMax-H3-Image-4bit",
  "source": "huggingface",
  "revision": "verified-commit-or-main",
  "format": "mlx",
  "task": ["text-to-image", "image-editing"],
  "files": [{"path": "transformer/model-00001...", "size": 0, "sha256": ""}],
  "license": "minimax-h3-image-community-license-agreement",
  "runtimes": ["mlx-vlm"],
    "verifiedAt": "2026-11-15T00:00:00Z"
}
```

## 6. 下载任务机制

任务状态统一为：

```text
queued -> resolving -> downloading -> verifying -> installed -> ready
                         |             |
                      stalled       failed -> retrying
```

核心能力：

- 单任务限速和全局带宽上限。
- 同时下载任务数、单文件连接数可调。
- 自动创建临时目录，完成后原子移动，避免半成品被运行时误识别。
- 失败分类：DNS、代理拒绝、TLS、HTTP 403/404、磁盘不足、校验失败、源站超时。
- 失败自动退避，切换源后再试；用户可点击“继续”“换源”“重新校验”。
- 任务与机器重启无关，服务恢复后从 SQLite 状态和 `.aria2` 断点继续。
- 下载完成后校验文件数量、大小、sha256 和必要配置文件。
- `stalled` 检测默认 120 秒无字节增长；检测到后自动重启当前文件最多 2 次，再切换源。

## 7. 运行模型

下载只是安装的一半。Runtime Adapter 负责把模型变成可用能力。

### 7.1 运行时选择原则

运行时不是“按文件扩展名猜”，而是由三项共同决定：模型格式、主机能力、已安装运行时。每个适配器实现统一接口：

```text
Detect() -> RuntimeInfo
CanRun(model, host) -> CompatibilityResult
Install(model, options) -> InstallResult
Start(model, options) -> Instance
Stop(instance) / Health(instance) / Logs(instance)
```

这样同一个模型可以明确显示“可下载”“可安装”“可运行”“已验证运行”四种状态。

### 7.2 MLX

- 检测 Apple Silicon 和统一内存。
- 根据模型 manifest 创建独立 Python/uv 环境。
- 支持 `mlx-lm`、`mlx-vlm`、`mlx-audio` 等运行时。
- 记录实际包版本、Git revision、启动参数。
- 提供文生文、文生图、图生图、视觉理解等标准动作。

### 7.3 Ollama

- 检测本机 Ollama 服务。
- 调用 Ollama API 获取模型列表、拉取、运行和健康状态。
- 不接管 Ollama 内部 blob；数据库只登记外部运行时和模型名称。

### 7.4 ComfyUI

- 检测 ComfyUI 安装目录和 models 子目录。
- 按模型类型创建链接或复制，并生成可验证的基础工作流。
- 显示“仅文件可见”和“工作流已验证”两个不同状态。
- 不把不兼容的 MLX 权重强行放入 ComfyUI。

### 7.5 llama.cpp / OpenAI 兼容服务

- 支持 GGUF 模型启动为本地 API 服务。
- 统一显示端口、上下文长度、GPU/Metal 参数和当前内存占用。
- 后续可接入 Open WebUI、Cherry Studio 等客户端。

## 8. Web 界面

第一版页面控制在 5 个：

1. **首页**：磁盘空间、运行中模型、下载速度、失败任务、可用运行时。
2. **模型市场**：关键词、任务类型、来源、大小、量化、内存、运行时筛选。
3. **下载任务**：总进度、单文件进度、速度、ETA、当前 URL、代理、错误和操作按钮。
4. **本地模型**：扫描结果、占用空间、重复文件、链接到哪些应用、删除/校验/迁移。
5. **运行实例**：启动、停止、日志、API 地址、健康检查和参数模板。

设置页提供：存储根目录、数据库位置、HTTP/HTTPS/SOCKS5 代理、`NO_PROXY`、按来源代理、下载并发、镜像优先级、磁盘保留空间、自动重试、运行时路径和日志保留时间。代理密码使用系统凭据存储，不回显、不写日志。

## 9. CLI 设计

```bash
modelhub search "MiniMax H3 Image"

modelhub install hf:nativ-community/MiniMax-H3-Image-4bit --runtime mlx-vlm
```

所有 CLI 命令与 Web API 共用同一套服务和数据库，避免出现“命令行看到的模型”和“网页看到的模型”不一致。

## 10. 安全与合规

- 默认只监听 `127.0.0.1`，不直接暴露到局域网或公网。
- 代理密码、HF token、ModelScope token 放系统凭据库：macOS Keychain、Windows Credential Manager、Linux Secret Service；不写 SQLite 和普通日志。
- 记录模型许可证、来源、revision 和下载时间。
- 安装前明确显示许可证和预计磁盘占用，禁止静默下载几十 GB。
- 自定义 URL 默认不执行仓库脚本、不自动安装任意 Python 依赖。
- 删除采用回收站/两阶段确认，先显示会影响哪些运行时链接。

## 11. 分阶段计划

### MVP 1：稳定下载和管理

- Go 服务 + SQLite + Vue Web UI。
- Hugging Face、ModelScope、本地目录三个来源。
- Go 原生下载器：代理、断点、分片、重试、校验、任务日志。
- Windows/Linux/macOS 硬件探测和模型兼容性推荐。
- 多模型根目录、磁盘统计、删除、迁移和导入。
- 前端通过 Vite 构建后由 `go:embed` 嵌入，发布单个 Go 二进制。

### MVP 2：运行能力

- MLX-LM/MLX-VLM 适配器。
- Ollama API 适配器。
- ComfyUI 目录链接和基础工作流。
- 本地模型一键运行、日志和健康检查。

### MVP 3：发现和迁移

- 可更新的常用模型目录。
- 模型兼容性评分和 M4 内存估算。
- 导出/导入模型清单，迁移到另一台 Mac 或 NAS。
- 可选局域网访问和用户认证。

## 12. 第一版验收标准

- 下载一个 50 GB 以上模型时，关闭终端、网络短暂断开、电脑重启后都能继续。
- 下载任务能区分“进程存在但无流量”和“正常下载”。
- 完成后自动检查所有必要文件，不能仅凭目录存在就标记成功。
- 同一文件在多个运行时之间不重复占用磁盘。
- `MiniMax-H3-Image-4bit` 能被识别为 MLX 图像模型，并能调用现有文生图/图生图脚本。
- 用户能看到模型的大小、量化格式、许可证、适配运行时和预计内存。
- 执行 `make build` 生成 Windows/Linux/macOS 目标二进制，并提供 `make install`、`make dev`、`make test`、`make release`。

建议的构建目标：

```bash
make build                       # 当前平台
make release                     # darwin-arm64/darwin-amd64/windows-amd64/linux-amd64/linux-arm64
```

前端构建只在开发机需要 Node.js；发布包内不带 Node.js，运行用户只拿到一个 Go 二进制和可选的模型目录。

## 13. 对现有脚本的迁移

当前 `download-model.sh`、`download-status.sh`、后台 `launchd` 任务可以作为下载引擎验证样例，不直接丢弃。第一版实现时应把已验证的经验迁移进去：

- Go 原生分片下载；
- 可选 aria2 加速通道，但不作为安装依赖；
- 代理显式传递；
- macOS 后台任务；
- `.aria2` 断点续传；
- stalled 检测；
- 自动重试和完整性验证；
- 模型目录与运行时目录分离。

这样这个工具不是从零猜测，而是把这次 54.5 GB 模型下载中暴露的问题固化为产品能力。
